# HR 练习平台 · 已知限制 v1（2026-10-10）

- 签发：本线（工程侧）
- 适用：`dist/hr-sql-practice.html` 网页端执行引擎（sql.js 1.14.2 / WASM 单线程）、题库与判题
- 口径说明：本文件只记**执行层面的已知限制**。**列名口径、容差口径、排序口径不在此重复**，
  一律以 `docs/caliber-ruling-v1.md`（裁定 1–6）为准。

## 限制 1 · 重查询无硬超时（WASM 单线程不可中断）

- **现象**：`vendor/sqljs/sql-wasm.js` 未导出 `sqlite3_interrupt`，也未安装 progress handler，
  `sqlite3_step` 执行中的中间计算无法从外部中断。查询一旦进入纯聚合 / 全排序，就没有硬超时兜底。
- **实测数字**（单进程 node 实跑）：
  - `SELECT COUNT(*) FROM HR_SALARY a, HR_SALARY b, HR_SALARY c` ≈ **6.52e9 行组合**，耗时 ≈ **90.7 秒**；
  - 对比项：两表 `COUNT(*)` **54 ms**；两表 `ORDER BY a.NetPay + b.NetPay` 全排序 ≈ **4 秒**。
- **影响面**：学员侧最坏表现为页面卡住数秒至数十秒，期间 UI 无响应。
- **触发条件**：三表及以上笛卡尔积 / 全量聚合 / 无索引约束的全排序，`MAX_ROWS` 对这类中间计算无效——
  **行数上限只限制「取出的行」，挡不住中间计算**。
- **兜底**：题型只出到单表 / 两表，学员侧最坏表现为页面卡住数秒。真修需 Worker 终止或等价机制
  （**未实现，属下一轮候选**）。

## 限制 2 · `MAX_ROWS = 1000` 是硬上限

- **现象**：结果集按 1000 行截断，被截断时置 `truncated = true`。
- **实测数字**：`SELECT * FROM HR_SALARY` 真结果 **1868 行**，会被截到 **1000 行**并置 `truncated = true`。
- **影响面**：当前 **120 题**参考答案最大 **200 行**（q018 / q068 / q069 / q072），不触发截断；
  若未来某题参考答案 >1000 行会被截断。
- **触发条件**：单条查询结果行数 >1000。
- **兜底**：参考侧被截断会触发 `expected.row_count` 对账提示「⚠ 题库待复核」（保守，**不会误判学员答错**、
  不扣心）。

## 限制 3 · 整型列上的 `/` 会静默整除（数据重建后答案可能漂移而不报错）

- **现象**：SQLite 与 T-SQL 一样，`/` 两侧都为整型时执行**整除**。派生库（`data/schema_sqlite.sql`）里
  天数列 / 人数列若被建成整型，`AVG(a / b)`、`SUM(a) / COUNT(*)` 这类写法会**静默**改结果——不抛错、不告警，
  只是答案偏小。q031 就是这样被独立复核抓出来的：`ActualDays / WorkDays` 在整型行上退化为整除，
  月出勤率偏低；权威 T-SQL 侧的原始写法同样有此风险。
- **已修事实（2026-10-10）**：q031 参考写法改为 `ROUND(AVG(1.0 * ActualDays / WorkDays) * 100, 1)`（两引擎一致），
  并新增 `dialect_note` 说明「显式乘 1.0 触发浮点除法，列类型即使被建成整型也不会被截断」。
- **仍依赖列类型的小数题**：q089 / q098 的人均应发依赖 `GrossPay` 为小数型（`SUM(GrossPay) / COUNT(*)`）。
  当前 schema 下正确，但**一旦重建库把金额列改成整型，需同样补 `1.0 *` 或 `CAST(... AS REAL)`**。
- **触发条件**：重建数据库 / 重新生成 schema / 改列类型。
- **兜底（重建后必跑）**：`npm run verify` —— 用真实 sql.js 重建库、逐题跑参考 SQL 与 `expected` 对账，
  120 题全绿才可发布；失败会打印题号与差异行。
- **未验证面**：T-SQL 参考写法**未在真 SQL Server 上验证**（当前只保证 SQLite 派生写法与 `expected` 一致）。
  条件具备时抽样验证 `dbo.` 侧写法。

## 限制 4 · 94 题逐行判分：行序写错会判错（提示必须先在展示层说清）

- **现象**：120 题中 **94 题**为逐行判分（`expected.order_sensitive = true`），学员内容全对但行序不同即判错。
- **影响面**：若题面与输出提示都没写排序要求，学员就在不知情的情况下被扣分——属「暗坑」而非教学点。
- **已闭合（2026-10-10 口径对齐）**：全库已按不变式拉平——「题面或输出提示写明排序」⟺ `order_sensitive = true`，
  两边各 **94 题**、双向差集为空；26 题的输出提示补写了行序表述（顺序取自参考写法 `ORDER BY`，与题面一致）。
- **平台侧守门**：`test/display.test.mjs` 两例不变式单测（`true` 必须说、`false` 不许说），入题库前自动拦漂移。
- **口径权威源**：HRIS《修订说明_行序口径对齐_20261010》；定义写进 `docs/questions-contract-v1.md` 第 4 节。
