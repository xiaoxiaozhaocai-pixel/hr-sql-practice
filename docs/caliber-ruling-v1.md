## 裁定 1 · 「在职」口径：**以基准日时点口径为准 = 174 人**

- **报表口径（对外统一）**：基准日 `2026-06-30` 时点在职。
  `任职记录 StartDate <= '2026-06-30' AND (EndDate IS NULL OR EndDate >= '2026-06-30')`，并按人去重。
- **花名册口径（仅作对比教学）**：`HR_EMPLOYEE.TermDate IS NULL` = **170 人**。
- 两者差 **4 人**（已提离职、离职日未到）。任何题干提到"在职/在编"**必须写明用的是哪一个口径**，否则一题两答。
- 题库体现：q001 用花名册口径（170）、q013 用时点口径（174），两题并列，专门练这个差别。

## 裁定 2 · 任职表日期倒挂数据：**保留，不修数据**

- 库内保留 3 行 `EndDate < StartDate` 的异常任职（ID 72 / 208 / 220），作为"数据质量排查"的练习素材。
- 权威源 `schema.sql` 中的 `CK_HR_ASSIGNMENT_DateOrder` **已移除**，原约束以注释留档说明；SQLite 派生版同样不启用该约束。
- 由此：**"改数据让约束成立"的做法一律否决**。练它的题目为 q009。

## 裁定 3 · 字符串比较语义：**题库规避 ＋ 网页端按 SQLite 实跑判题**

- SQL Server 裸 `=` 默认忽略大小写与尾空格，SQLite 逐字精确——这是本次唯一会改变个别题答案的差异点。
- 判题基准 = **在同一个 SQLite 实例上跑参考 SQL 得到预期结果集**（契约方案 A），因此两方言语义差异**不会**造成误判。
- 题干若涉及字符串匹配，必须写明用 `UPPER()` / `TRIM()` 或 `LIKE`。已落地 q015（字典翻译需 TRIM）。

## 裁定 4 · 展示顺序：**不重排题库，改为网页端可选排序**

- 题库保持"难度递增 ＋ 同层易错优先"（L1 五题 / L2 七题 / L3 六题 / L4 两题；视图题自 q013 起）。
- 易错重点已通过 `tags`、`pitfalls`、`knowledge_point` 暴露，**网页端提供按考点/难度/易错标签筛选与排序**即可，不要求改题库物理顺序。

## 裁定 6 · 列名口径：**列数必须一致；列名不比对**（2026-10-10）

业务侧 2026-10-10 书面裁定：

- **列数必须一致**；**列数不一致判不通过**（结论里列出两边列数）。
- **列名不比对**：别名、大小写、单复数、中英文差异一律不判错；列顺序不敏感。
- `output_hint` 的列名要求属**教学提示**，**不进判题**。
- 工程侧实现无需改动（现有判题引擎与裁定 6 一致）。

## 裁定 8 · 判题「列名/列序对齐」分支：**保留，不删**（2026-10-18）

工程侧曾被要求「清理判题代码里残留的列名归一化比较分支（哪怕死代码）」。**实测该前置不成立，裁定保留。**

- 该分支不是死代码，是裁定 6「列序不敏感」的实现载体：`src/judge.js` 的 `buildNamePermutation()` / `applyPermutation()` 用在 `judgeResult()` 的 `nameEq` 上，而 `verdict.pass = nameEq || posEq`。删掉即等于「列序不同判错」，与裁定 6 直接冲突。
- 另有 `namesSetEqual()` 只喂 `columnIssue` 提示、**不参与通过与否**，也非死代码（有断言 `columnIssue` 非空的用例）。
- 验收用例（`test/judge.test.mjs`，两条硬断言，删分支必红）：
  - L54–56 列名不同但列序一致 → `pass=true` / `alignMode='position'` / `columnIssue` 非空
  - L63–64 列序不同但列名可匹配 → `alignMode='name'` / `columnIssue=null`
- 结论：分支**在用**、有独立用例、与裁定 6 同向。「避免死代码」的动机可成立，但对象不是这段代码。
